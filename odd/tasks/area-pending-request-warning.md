# AREA Pending Request Warning

## Objective
Warn AREA operators audibly about unhandled service requests every three minutes, in both the foreground web console and Android background, until no request remains `PENDING`.

## Problem and why
The one-time arrival alert can be missed or ignored while a guest waits. A recurring warning should bring overdue requests back to the operator's attention.

## Authorized scope and constraints
- Implement the AREA web foreground warning and native Android background warning; do not change ROOM, server request semantics, or DND behavior.
- A newly received `PENDING` request resets the three-minute interval. Repeat every three minutes while any request remains pending; cancel when none remain. Hiding/dismissing a modal does not count as handling a request.
- Use one audio owner per runtime: the Android watchdog owns reminders in both Android app foreground and background; the web watchdog runs only in browser-only AREA consoles without a native bridge. Seed/reconcile Android state from authoritative snapshots and status updates.
- Reuse existing request-warning playback unless implementation evidence requires a distinct sound. Do not add a visual modal for each reminder.
- Preserve the existing dirty checkout and staged index; only isolate this feature's changes for work-unit commits. Current branch: `jorlys/feat/lan-notification-agent` (already a feature branch).
- Before each commit, recheck Git state. Git rejects `git commit --only --patch`; instead use a temporary index initialized from `HEAD`, stage only feature hunks/files there, inspect its staged diff, and commit from that index. Reconcile the real index only for a committed path that had no prior staged changes; never reset or overwrite the user's existing staged state.
- Android source changes require an APK build and installation on both user-specified devices. The user grants standing authorization to install every new/modified APK via the previously used ADB session on `R9PT70GX3PA` and `192.168.0.243:44999`; do not ask again for per-build authorization.

## Acceptance criteria
1. In the web AREA console, every newly observed pending request resets the warning deadline; reminders sound at three-minute intervals, including after hydration of already-overdue requests.
2. In native Android background operation, authoritative snapshot hydration and subsequent request status updates keep the pending set correct; warnings repeat on the same cadence and stop when no request is pending.
3. Foreground/background transitions never double-play reminders: Android has one native owner in both states, while browser-only consoles use the web owner; modal dismissal alone does not stop reminders.
4. Focused tests, full applicable unit suites, Android debug build, and `git diff --check` pass. The resulting APK is installed on both user-authorized devices after each build.
